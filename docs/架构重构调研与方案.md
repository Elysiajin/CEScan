# CEScan 架构重构调研与方案

## 1. 结论

当前项目最严重的问题不是“模块职责不明”，而是：

1. `main_gui.cpp` 是 8729 行的上帝翻译单元，把 Win32 视图、输入解析、扫描/调试业务、符号解析、DBVM 单例操作、自绘控件、GIF 解码全部混在一起。
2. 构建系统历史上至少有三套互相冲突的手写源文件列表：`CMakeLists.txt` 曾只做 CLI，`CEScan.vcxproj` 只做 GUI，`build.bat` 想同时做两者但源列表陈旧并缺少 `HookRestore`、`ThreadLocator`，GUI 会链接失败。（2025-01 已按“只保留 GUI”决策收敛，详见 2.2。）
3. 全局对象 `App g` 同时持有 `ProcessMemory`、`ScanEngine`、`Debugger`、`McpClient` 和全部 MDI 窗口状态，所有后台线程都通过裸指针 `PostMessage` 与全局状态交互。
4. `DBVM` 功能被 GUI 直接摸 `DbvmTools::Instance()` 单例，缺少服务层和可测试边界。
5. 存在 `Gui.cpp` 等死代码；备份文件与编译产物已清理（2025-01），git 仓库已建立并推送初始快照，重构安全网已就位。

重构目标不是重写，而是把现有功能按“核心域、域服务、UI 视图”三层拆开，每个层只通过明确接口通信，最终让 GUI 单文件不再是全项目依赖中心。

本次调研只做静态源码检查，没有执行编译、链接或真实附加调试；下列“行为保持”都是验收目标，不是已验证事实。

## 2. 现状快照

### 2.1 文件规模

| 文件 | 职责 | 规模/说明 |
|---|---|---|
| `src/main_gui.cpp` | GUI 主文件 | ~8729 行，包含全部 MDI 子窗口、调试 UI、DBVM UI、扫描 UI、符号解析、自绘控件、GIF 解码 |
| ~~`src/main.cpp`~~ | ~~CLI 入口~~ | 2025-01 删除：用户确认只保留 GUI 版本 |
| `src/Gui.cpp` | 旧 GUI | ~600 行，无任何构建脚本/CMake/vcxproj 引用，是死代码 |
| `src/ScanEngine.cpp` | 扫描引擎 | 相对健康，只依赖扫描相关核心类型 |
| `src/Debugger.cpp` | 调试循环 | 相对健康，通过回调向 UI 报告事件 |
| `src/HookRestore.cpp` | Hook/还原分析 | 核心域，可独立理解 |
| `src/ThreadLocator.cpp` | 线程定位窗口 | 独立自绘 UI，是“可复制的拆分模板” |
| `include/*` | 17 个头文件 | 底层依赖基本单向，主要问题在上层 GUI |
| `tests/` | 测试/靶子 | 有 dbvm、hook_restore、disasm、hwbp、watch 等目录，尚未接入统一测试框架 |

### 2.2 构建系统冲突

| 构建入口 | 行为 | 问题 |
|---|---|---|
| `CMakeLists.txt` | 只构建 GUI `CEScan`（2025-01 起移除 CLI 后） | 曾只构建 CLI（`src/main.cpp`），GUI/Debugger/DBVM/HookRestore 都不构建；现已与 GUI 对齐 |
| `CEScan.vcxproj:41-57` | 只构建 GUI `CEScan` | 与 CMake 现已一致 |
| `build.bat` | 构建 GUI（2025-01 起移除 CLI 后） | 曾同时构建 CLI + GUI 但 `SOURCES` 和 GUI 链接列表缺 `HookRestore`、`ThreadLocator`，脚本已陈旧；现已修复并只产出 GUI |
| `一键编译.bat` | 构建 GUI（同上） | 与 `build.bat` 重复，两者互相覆盖 |
| `一键编译_BuildEnv.bat` | 构建 GUI | 产物曾叫 `bin/CEdbg.exe`，与其它入口不一致；现已统一为 `bin/CEScan.exe` |
| `build_gui.sh` | 构建 GUI | 产物曾叫 `bin/CEdbg.exe`，现已统一 |
| `CEScan.sln` | 打开 vcxproj | 与 CMake/一键脚本产生不同的目标结构 |

由此带来三个实际问题：

- `bin/CEScan.exe` 可能被 CLI 或 GUI 覆盖，取决于最后一次使用哪个构建入口。
- 手抄源文件列表已经出现真实漂移，`build.bat` 的 GUI 必然缺符号。
- 无法用一套命令复现“完整可发布版本”。

### 2.3 依赖关系

当前 include 依赖大体是单向的：

- 最底层：`CETypes`
- 基础工具：`CEUtil`、`Disasm`、`PatternScan`
- 核心服务：`ProcessMemory`、`RegionFilter`
- 域服务：`ScanEngine`
- 调试域：`Debugger`、`HookRestore`
- 驱动域：`DBVM`、`DbvmLoader`、`DbvmTools`
- 独立工具：`McpClient`、`StrSearch`
- UI 域：`main_gui.cpp` include 了几乎所有头文件

`ThreadLocator` 是少数已经具备边界感的模块：它接受 `Debugger*`、状态/日志回调，自己维护窗口和命中状态，不引用 `App g`。新拆分可以复用这种模式。

### 2.4 `main_gui.cpp` 的耦合证据

`src/main_gui.cpp:337-441` 定义 `struct App`，`:441` 立即声明 `static App g;`。`App` 至少同时持有：

- 主窗口、状态栏、工具栏和 9 个 MDI 子窗口句柄；
- `ProcessMemory proc`；
- `ScanEngine scan{proc}`；
- `Debugger dbg`；
- `McpClient mcpClient`；
- 扫描状态、字符串搜索结果、MCP 连接状态；
- CPU 四面板的全部视口状态和分割比例；
- 字体、主题、driverLoaded 等环境状态。

项目里还有大量文件级全局状态，例如 `g_statusText`、`g_pendingLog`、`g_pendingLogData`、`g_guardWatchOn`、`g_guardWatchAddr`、`g_watchGen`、`g_hitInFlight`、`g_apiNameCache`、`g_exportCache`、`g_pdLogos`、`g_watch`、`g_restoreJournal`、`g_titleTag`。

跨线程通信不是稳定接口，而是“裸 `new` + `PostMessage` + UI 线程 `delete`”：

- `AddLogLine`（`src/main_gui.cpp:543-546`）把 `new std::string(text)` 直接发给 `g.frame`；
- `LogDataAdd`（`:574-577`）把 `new std::wstring(addr + "|" + msg)` 直接发出去；
- `OnDebugHit`（`:833-841`）把 `new HitReport(hit)` 发给 `WM_APP_HIT`，超过 `kMaxHitInFlight=2000` 就丢样本；
- 扫描线程（`:927-954`）直接操作 `g.scan`、`g.scanning` 和 `g.frame`；
- `std::thread(...).detach()` 让后台任务没有生命周期管理。

自定义消息编号集中在 `:325-335`，消息携带裸指针，任何一对 `PostMessage/处理函数` 都必须同步遵守“谁分配、谁释放、哪个线程处理”的约定。这很容易在拆分视图时漏掉。

`ProcessMemory` 还存在跨线程风险。代码里有明确注释说明：

- 调试线程不能碰 `g.proc.CachedModules()`，因为它是懒加载且无锁；
- Watch 后台线程自己再开一份 `ce::ProcessMemory own`，避免和 UI 线程共享缓存；
- 扫描线程则直接操作共享 `g.scan` 与 `g.proc`。

这证明当前架构靠“注释约定人肉保证线程安全”，而非语言/接口保证。

DBVM 部分没有服务边界。大量代码直接调用 `ce::DbvmTools::Instance()`，例如设置断点、恢复冻结线程、CloakProtect、修改寄存器、Trace、物理读写等（`src/main_gui.cpp:6007-6173` 一带）。GUI 卸载时还要依赖 `WM_DESTROY` 里手动 `KillTimer → TlShutdown → mcp.Disconnect → dbg.Detach`，不是 RAII 作用域。

## 3. 重构目标

长期目标架构：

```text
app/
  MainFrame.cpp           窗口创建、菜单、快捷键、消息循环、应用生命周期
  Session.cpp             目标进程/调试/DBVM 会话状态，创建并持有域服务
  UiDispatcher.cpp        后台线程 → UI 线程的安全消息总线

ui/
  views/CpuView.*         反汇编、寄存器、DUMP、STACK
  views/ScanView.*        扫描参数、进度、结果、写入
  views/MapView.*         模块/内存区
  views/ThreadsView.*     线程
  views/BpView.*          断点
  views/LogView.*  LogDataView.*
  views/McpView.*
  views/StrView.*
  views/WatchView.*
  views/ProcAttachDialog.*
  views/SettingsView.*
  views/ThreadLocatorView.*（吸收现有 ThreadLocator，但不改其边界）
  theme/*  controls/*

services/
  SymbolResolver.*        PE 导出解析、API 名缓存、反汇编注释
  WatchService.*          页守卫监视、命中分类、异步轮次
  RestoreService.*        Hook 分析/还原流程，接管 restore_trace 与日志
  DbvmService.*           驱动加载、DBVM、DbvmTools 的唯一入口
  McpService.*            MCP 连接和命令状态
  SessionService.*        目标进程/调试器句柄、附加/脱离生命周期

core/                    保留现有核心模块，按需整理目录
  CETypes/ CEUtil/ Disasm/ PatternScan/
  ProcessMemory/ RegionFilter/ ScanEngine/
  Debugger/ HookRestore/ StrSearch/ DbvmLoader/ DBVM/ DbvmTools/
  McpClient/
```

分层原则：

1. `core/` 只允许依赖更低层 `core/` 或标准库，不依赖 Win32 UI。
2. `services/` 可以依赖 `core/`，负责跨线程任务与状态机，不直接创建窗口。
3. `ui/views/` 只通过服务接口和 `UiDispatcher` 获取数据，不直接操作其它视图的全局状态。
4. `app/Session` 是唯一持有 `ProcessMemory`、`ScanEngine`、`Debugger`、`DbvmService` 生命周期的地方，GUI 视图通过它拿只读会话信息。
5. 只有 `app/` 和 `ui/` 可以调用 Win32 UI API；`core/` 和 `services/` 不 include `windows.h` UI 相关依赖，除非是底层 OS API。

“完全删除单例”不是目标。`Dbvm::Instance()` 这类底层物理设备句柄可以保留，但必须被 `DbvmService` 收口；GUI 不能再到处直连单例。

## 4. 分阶段重构方案

每阶段都要求可编译、行为不后退，并保证可以单独评审。

### Phase 0：统一构建与安全基线

目标：让 GUI 由同一套事实源构建，先消除手抄源列表漂移。

非目标：不改功能、不拆文件。

背景变更：2025-01 用户确认“去掉 CLI，只保留 GUI 版本”。`src/main.cpp`（931 行 CLI 入口）与 `src/main_entry.cpp`（入口胶水）已删除，所有构建入口统一只产出 `bin/CEScan.exe`（GUI）。Phase 0 因此不再涉及 CLI 目标。

做法：

1. 把公共源模块整理为 `cescan_core` 静态库；GUI 可执行目标 `cescan_gui` 只含 `main_gui.cpp` + 核心库。
2. `CMakeLists.txt` 成为唯一源列表事实源。
3. 更新 `CEScan.vcxproj`/`CEScan.sln`，或者改为 CMake 生成 VS 工程，避免两份工程手抄漂移。
4. `build.bat`、`一键编译.bat`、`一键编译_BuildEnv.bat`、`build_gui.sh` 改为调用同一 CMake 构建，产物名统一为 `bin/CEScan.exe`。
5. 若必须保留便携 VC 手稿，把所有源列表抽成一个 `.cmake`/清单文件，脚本读取它，禁止继续手抄两份。

接口/验收：

- 一套命令产出 GUI。
- `build.bat` 不再因缺 `HookRestore`/`ThreadLocator` 链接失败。
- 只有一个 exe 名 `bin/CEScan.exe`，不再出现 `CEdbg.exe`/`CEScanGUI.exe` 混用。
- 打开 `CEScan.sln` 也能得到同样产物来源，或明确改为 CMake 工程。

风险：

- 便携 VC 工具链版本可能不支持项目当前头部用法；应先记录当前能成功构建的确切命令行和 MSVC 版本。
- 改构建不影响逻辑，但 CMake/VS 目标之间可能存在已存在但没人触发过的编译差异；Phase 0 先把两种构建都跑通再进入拆代码。

### Phase 1：把 GUI 内的域逻辑抽成服务

目标：先让业务逻辑可测试，再拆窗口。

非目标：不追求一次完成所有视图拆分。

优先抽取：

1. `SymbolResolver`：把 `BuildExportMap`、`ResolveApiName`、`g_apiNameCache`、`g_exportCache`、反汇编符号注释抽到一个类，输入 `ProcessMemory` 或模块句柄，输出符号结果。它不应知道 `HWND`、`g.frame` 或消息编号。
2. `UiDispatcher`：实现投递 `std::function`/类型化事件到 UI 线程的安全队列，替代裸指针 `WM_APP_*`。扫描、命中、日志、日志数据、MCP 状态、字符串搜索都改走 dispatcher。
3. `WatchService`：把 `WM_APP_HIT` 轮次号、`kMaxHitInFlight`、页守卫状态、命中分类放进一个服务对象，UI 只订阅结果。
4. `DbvmService`：把 `SharedDbvmLoader` 和所有 `DbvmTools::Instance()` 调用收口；GUI 只调用 `DbvmService` 方法。
5. `Session`：先建立“附加目标、调试会话、DBVM 状态”同心智对象，`main_gui` 仍可持有它的引用，但后台线程不再直接抓 `g.proc`/`g.scan`/`g.dbg` 裸对象。

接口/验收：

- `main_gui.cpp` 中不再出现自行 `new` + `PostMessage` 传递 `std::string`/`HitReport` 的代码。
- `SymbolResolver`/`WatchService`/`RestoreService` 有纯逻辑单测，至少覆盖 PE 导出解析、API 名匹配、命中轮次、在途上限。
- 原有调试、扫描、Watch、DBVM 功能行为保持不变，先不重写实现。

风险：

- 消息语义变化最容易漏“UI 窗口还没创建时先缓存，创建后补发”的状态；`UiDispatcher` 必须把尚未创建窗口的事件缓存/丢弃策略做成显式状态。
- 服务抽取若先移动线程调度，会把线程 bug 和功能重构混在一起；建议先抽纯逻辑，再把线程入口改为服务方法。

### Phase 2：把 MDI 子窗口拆成独立视图

目标：把 8729 行的 `main_gui.cpp` 降到可维护规模，每个视图一个文件。

做法：

1. 为 9 类 MDI 子窗口各建一个 `View` 类，接口统一为：
   - `Init(HWND child, Session&, Theme&)`
   - `Layout(int w, int h)`
   - `OnCommand/Hook/wParam/lParam`
   - `Refresh()`
   - `OnDestroy()`
2. `App` 简化为窗口注册、工具栏、菜单、快捷键和视图容器，不再保存每个视口内部的滚动位置、列宽、拆分比例等状态。
3. 视图通过 `SetWindowLongPtr(GWLP_USERDATA, this)` 绑定窗口，`WM_NCCDESTROY` 负责销毁视图对象，避免 `PostMessage` 发给已销毁窗口。
4. CPU 四面板可以拆成 `CpuView` 一个目录内部四个组件，不强制一次拆成 4 个顶层文件。
5. `ThemeColors` 只做主题数据与颜色计算，不再散落各处。

接口/验收：

- `main_gui.cpp` 行数降到约 1500 以内，且剩余内容主要是 `MainFrame`/`wWinMain`/窗口注册。
- `rg` 不得发现某个视图通过另一个视图的文件级静态变量改状态。
- 所有 `Ctrl(child, IDC_*)` 都归属对应视图，不跨视图访问。
- CPU、扫描、字符串、Map、日志、Watch 等窗口创建/销毁后重开不崩溃、不丢状态。

风险：

- Watch/日志是异步高频路径，最容易出现“视图已销毁、回调还在”的悬空窗口问题；必须由 `UiDispatcher` 和 Session 生命周期统一兜底。
- 自绘控件拆分时不要重写绘制代码；先把自绘控件移动到 `ui/controls/`，再让各视图复用。若先改绘制逻辑，会同时引入视觉回归和结构风险。

### Phase 3：生命周期、线程模型与全局状态收口

目标：消除 `static App g` 之外的隐藏全局状态、后台线程逃逸和手动 `WM_DESTROY` 清理。

做法：

1. `Session` 用 RAII/显式 `Shutdown()` 管理 `TlShutdown`、MCP 断开、调试器 Detach、DBVM 释放；退出路径统一，不依赖消息顺序。
2. 后台任务从 `std::thread(...).detach()` 改为可取消的 `TaskHandle`/线程池任务，并保证任务结束时 UI 回调不再投递。
3. `ProcessMemory::CachedModules()` 加递归锁或返回快照，消除“不能从后台线程碰 g.proc”的注释型约定。
4. 把 `g_watch`、`g_restoreJournal`、`g_apiNameCache`、`g_exportCache` 等移动到对应服务对象。
5. 启动配置（`CE_W_*`、字体、主题、随机标题）收进 `AppConfig`/`ThemeConfig`。

接口/验收：

- `static App g` 不再是其它文件可见的全局；即使保留一个 `App*` 应用上下文，也不能让服务层依赖它。
- 调试事件、扫描、Watch、MCP、字符串搜索都通过 dispatcher 或服务回调，不再有裸 `PostMessage` 指针。
- 退出时有清理日志或可断言的唯一路径，双击关闭、菜单退出、CrashFilter 路径都能释放会话。
- `ProcessMemory` 后台线程安全性可以用并发测试或至少用 ThreadSanitizer（若 MSVC 支持）/静态分析检查。

风险：

- Win32 回调生命周期调整属于高风险改动，建议每拆一个视图先跑一遍对应流程。
- 线程模型改动后，性能可能在页守卫高频命中场景变化；验收时应保留现有 `kMaxHitInFlight` 丢样策略，并允许继续调参，但不允许用 UI 卡死换取不漏样本。

### Phase 4：测试、死代码与知识沉淀

目标：让重构从“一次性大改”变成可持续演进。

做法：

1. 把 `tests/` 接入 CTest 或统一测试脚本，核心纯逻辑必须有单测。
2. 给 GUI 建立可自动化的冒烟测试：启动、窗口创建、无进程参数时的行为、非法输入路径。
3. 建立“构建 → GUI 启动 → 手工附加到靶进程”的验收清单。
4. `Gui.cpp` 等死代码归档到 `archive/` 或外部备份，但只在确认无引用后处理；先建议保留，不做物理删除。
5. 如果条件允许，先初始化 git 并做一次提交；即使不迁移平台，也有完整回滚点。（已完成：仓库已初始化并推送初始快照到 GitHub）

接口/验收：

- `cmake --build` 通过，GUI 能启动并完成附加/扫描/调试/Watch/DBVM 主路径。
- `rg "Gui.cpp|main_gui.cpp.bak|DbvmTools::Instance|PostMessage.*WM_APP"` 的结果符合新架构白名单。
- 每个纯模块新增测试不是复制实现，而是验证真实边界行为。

## 5. 建议执行顺序

建议按“先构建、再服务、再视图、再生命周期、最后清理”的顺序执行：

1. 先跑通当前三个构建入口，记录哪些能成功、哪些失败，避免把基线错误带进重构。
2. Phase 0 统一构建，最快消除“代码写好了但无法产出 GUI”的摩擦。
3. Phase 1 抽取符号解析、dispatcher、Watch、DBVM 服务，这是技术债集中点，先消化。
4. Phase 2 拆 MDI 视图，优先拆 `ScanView` 和 `LogView` 这两个状态简单、风险低的窗口，再拆 `CpuView` 和 `WatchView`。
5. Phase 3 收线程与生命周期。
6. Phase 4 清理死代码、补测试和文档。

建议不要做：

- 不要同时“重写 Win32 UI 框架”和“重构模块”，会把两套变更混在一起。
- 不要一开始就删除 `Gui.cpp`/备份，应先确认历史信息不需要。
- 不要继续新增第三份手抄构建入口；所有新能力都接入统一构建。
- 不要把 `DbvmTools` 单纯改成“不用单例”而引入新的全局 Session，应在 App/Session 拥有它。

## 5.5 其他架构问题（补充调研）

以下问题在首轮调研后补充发现，均有代码证据，且会改变后续阶段的任务清单。

### 5.5.1 三套各自独立的诊断日志，路径与开关策略不一致

| 设施 | 位置 | 触发条件 | 输出位置 |
|---|---|---|---|
| `UiTrace` | `src/main_gui.cpp:484` | `CE_UITRACE=1` | exe 同目录 `ui_trace.txt` |
| `RTrace` | `src/main_gui.cpp:523` | `CE_RESTORE_TIMING=1` | CWD 相对 `restore_trace.txt` |
| `CrashFilter` | `src/main_gui.cpp:8365` | 无条件，每次崩溃都写 | CWD 相对 `crash.txt` |

问题：

- `CrashFilter` 没有开关，无法关闭；
- 写入路径两种策略混用（`GetModuleFileNameA` 定位 exe 目录 vs 相对 CWD），从不同工作目录启动时落点不同；
- 三者都是 `fopen("ab") + fprintf + fclose`，无崩溃安全保证；`CrashFilter` 里只有 `static LONG s_busy` 做重入守卫，不能保证文件完整。

### 5.5.2 第二条 UI 刷新链路：轮询定时器

`src/main_gui.cpp:7906-7907` 在主窗上设两个定时器：

- `SetTimer(hwnd, 1, 500)`：`main_gui.cpp:7934` 只要 `g.dbg.IsAttached()` 就 `UpdateCpuWindow()` + 刷状态栏 + 刷标题；
- `SetTimer(hwnd, 2, 3000)`：`main_gui.cpp:7929` 每 3 秒 `ce::JfDriverLoaded()` 探测驱动在线状态，写 `g.driverLoaded`。

这使 CPU 视图存在**并行的两条数据来源**：WM_APP 消息链路（事件驱动）和 500ms 轮询（时间驱动）。后者在调试 loop 线程运行期间持续读 `g.dbg` 状态。驱动状态检测用轮询而非设备通知，也意味着 `DbvmLoader` 模块被 UI 定时器直接依赖。

### 5.5.3 `DbvmTools` 退出路径缺失

`src/main_gui.cpp:8348-8354` 的 `WM_DESTROY` 只做 `KillTimer(1) → TlShutdown() → mcpClient.Disconnect() → g.dbg.Detach()`，**没有停 `DbvmTools`**。

`DbvmTools` 是静态单例（`include/DbvmTools.h:46`），内部持有 `std::thread resumerThread_`（`include/DbvmTools.h:119`；`src/DbvmTools.cpp:28-37` 的 `Start()` 起线程、`Stop()` join）。它的停止只发生在 `~DbvmTools()`（`src/DbvmTools.cpp:26`），即进程退出时的静态对象析构——此时主线程已 `PostQuitMessage`，`wWinMain` 即将返回。静态析构顺序跨编译单元不确定，`DbvmTools` 析构 join 的 resumer 线程可能触达已销毁的 UI 状态。

结论：`DbvmService::Shutdown()` 必须在 `WM_DESTROY` 里与 `dbg.Detach()` 并列显式调用，不能留给静态析构。

### 5.5.4 DBVM 命中回调不受 dispatcher 约束

`include/DbvmTools.h:105` 的 `SetHitCallback` 是直接赋值 `hitCb_`，没有线程调度；`src/main_gui.cpp:8639` 在 `wWinMain` 里把它设成 `DbvmOnHit`。该回调由 `DbvmTools` 的 resumer 线程触发（`SetBreakpoint` 在 `src/DbvmTools.cpp:73` 调 `Start()` 拉起该线程）。

与调试命中链路对比：`OnDebugHit`（`src/main_gui.cpp:833`）走 `PostMessage` + `UiDispatcher` 待改造路径，而 DBVM 命中是**同步回调**。这是第二条不受统一消息机制约束的跨线程入口。`DbvmOnHit` 若触碰 UI 或全局状态即为竞态；GUI 还通过同一单例下断点、改寄存器、读日志。

### 5.5.5 符号解析缓存策略分裂

`BuildExportMap` 定义在 `src/main_gui.cpp:1021`，三个调用点的缓存行为不同：

- `:1094` `ResolveApiName`——有 `g_exportCache` / `g_apiNameCache` 缓存；
- `:5737` `ApbApplyByKeys`——**无缓存**，每次点菜单都对 `g.proc.CachedModules()` 全量重扫导出表后逐个 `SetInt3`；
- `:5819` `ApbCustomInput`——同样无缓存。

同一次操作的结果不写回缓存，重复操作重复全量解析。模块多时这是 UI 线程上的可感知阻塞。这不只是分层洁癖问题，是缓存策略分裂导致的性能缺陷。

### 5.5.6 链接依赖散落在 `#pragma comment(lib)` 里

grep 到 28 处，分布在 `src/main_gui.cpp:206-209`（comctl32/uxtheme/psapi）、`src/ProcessMemory.cpp:14`（psapi）、`src/McpClient.cpp:14`（ws2_32）、`src/ThreadLocator.cpp:35-37`、`src/Gui.cpp:25-26` 等。

不使用 `#pragma comment(lib)` 的构建系统必须手工列库：历史上 `build.bat:83,87` 和 `一键编译.bat:87` 各自列一份不同的库清单（user32/advapi32/ole32/ws2_32/winhttp/oleaut/comdlg/comctl/uxtheme…）。新增一个 Win32 API 调用就要同步改多处脚本——这是构建漂移在库依赖层面的形态。2025-01 已把 CMake 的链接库补齐到 GUI 全量（psapi/user32/advapi32/ole32/oleaut32/comdlg32/comctl32/gdi32/ws2_32/winhttp/uxtheme）。

### 5.5.8 对阶段计划的修正

补充调研导致以下调整：

1. **Phase 0 增加一步**：把散落的 `#pragma comment(lib)` 依赖收敛为各构建目标显式的 `target_link_libraries`，作为统一构建的验收项之一。
2. **Phase 1 增加任务**：`UiDispatcher` 的收口范围从“裸 `PostMessage` 指针”扩大到包含 `DbvmTools::SetHitCallback`，使 DBVM 命中与调试命中走同一条异步链路。
3. **Phase 3 增加任务**：`WM_DESTROY` 序列显式加入 `DbvmService::Shutdown()`，与 `dbg.Detach()` 并列；同时处理两个轮询定时器的归属（驱动检测与 CPU 刷新应改为事件驱动或有明确所有者的周期任务）。
4. **Phase 1 的 `SymbolResolver` 验收增加**：三个 `BuildExportMap` 调用点全部改为走服务且共享同一缓存，`ApbApplyByKeys`/`ApbCustomInput` 不再重复全量解析。
5. **三套诊断日志**合并为单一 `AppLog`/`Diagnostics` 模块，统一开关与输出路径，纳入 Phase 1。

6. **`Disasm` 引擎选型评估（Phase 1 内完成）**：现有 `src/Disasm.cpp` 是 403 行自研迷你引擎，`include/Disasm.h:3` 自我定位为“够用于调试器显示，不追求 100% 覆盖”。它缺少移位组 `C0/C1/D0-D3`、`cwde/cdq/cqo`(98/99)、`pushf/popf`(9C/9D)、`lahf/sahf`(9E/9F)、`int imm8`(CD)、`into`(CE)、`iret`(CF)、`xchg`(86/87)、`xadd/cmpxchg`(0F C0/C1/B0/B1)、`bt/bts/btr/bbt`、`bsf/bsr`、`popcnt`、`loop/loopne/jecxz`(E0-E3)、`in/out`(E4-E7/EC-EF)、全部 FPU/MMX/SSE/AVX 与 VEX 编码。未覆盖字节的兜底是 `src/Disasm.cpp:381-387` 的 `snprintf(buf, sizeof(buf), "db 0x%02X", op); r.text = buf; r.length = std::max<size_t>(c.pos, 1)`——**未覆盖的单字节 opcode 只按 1 字节计长，后续整条反汇编流水线错位**，直接影响 `src/HookRestore.cpp:258-265` 的 `SolveRestore` 对齐判定（`db ` 前缀或 `pos != hookLen` 即判 aligned=false）和 `src/Debugger.cpp:664-676` 的 Trace Over 断点地址计算。
   评估清单（三项都要给出结论，禁止只凭印象选型）：
   - 继续自研：列出必须补齐的指令分组优先级，说明为什么这些分组对本项目的 HookRestore/CPU 面板是刚需；工作量按“每个分组 ModRM+SIB+立即数组合”估算，不接受“大概几百行”这种无依据结论。
   - 引入 `thirdparty/udis86`：**它是纯反汇编库，不提供汇编能力**（`extern.h:45-106` 公开 API 中无任何 encode/emit/assemble 入口；`udis86.c:112` 的 `ud_asmprintf` 与 `types.h:195-199` 的 `asm_buf` 指的是反汇编文本输出缓冲，不是汇编器产物）。指令覆盖到 AVX/256 位为止（`itab.h:820-934` mnemonic 枚举 + `itab.c` 表），**无 AVX-512、BMI1/BMI2、ADX、FMA3**（EVEX 0x62 编码在 `decode.c` 中不存在，VEX 只判 `0xC4/0xC5`，见 `decode.c:1111-1137`）。优点是 2013 年停更但稳定、BSD 2-clause、无外部依赖、MSVC 可直接编（`extern.h:35-43` 处理了 `_USRDLL`/`LIBUDIS86_EXPORTS`；`udint.h:35-40` 的 assert 默认关闭）；`decode.c:81-124` 的 `inp_buf` 机制允许直接喂内存缓冲，不必走 FILE*。
   - 换成 Capstone 或 Zydis：本仓库没有源码，需评估许可（Capstone BSD-3、Zydis MIT）、MSVC v143 构建方式、AVX-512/BMI2 覆盖度，**未验证项必须标注**。
   无论选哪个，都必须补齐一条验收：`tests/disasm_test.cpp` 现有 24 个用例只覆盖 ModRM/SIB/REX/RIP 相对/立即数长度，**没有覆盖任何未支持指令**；替换或补全后，需要把自研引擎当前会输出 `db ` 的字节序列逐类加入回归测试，否则 HookRestore 的边界对齐仍然不可信。
   注意：`udis86` 的错误路径与自研兜底同病——`decode.c:1230-1262` 出错时清空指令数据并置 `UD_Iinvalid`，**但仍返回已消费的 `u->inp_ctr`**，所以换库不会自动解决长度可靠性，必须显式校验 `ud_insn_mnemonic() != UD_Iinvalid`。

## 6. 风险与开放问题

- 构建基线未验证：本报告没有运行编译/链接，实际 MSVC 版本、`/std` 支持度、DBVM 驱动加载依赖都可能影响 Phase 0 改动。
- `main_gui.cpp` 的部分原始边界只能通过运行验证：尤其是附加、退出、页守卫高频命中、DBVM 断点。
- 备份文件可能不是可丢弃内容：需要人工确认是否需要保留历史版本后再物理删除。
- 编码问题：仓库文件使用 UTF-8，脚本和构建参数不能无脑转码；改动时保持 `/utf-8`。
- `DBVM` 单例可能隐含驱动全局状态：重构时要先确认 `DbvmLoader::Unload`、`DbvmTools::Start/Stop` 的调用顺序，避免拆服务后破坏卸载路径。已知 `WM_DESTROY`（`src/main_gui.cpp:8348-8354`）未显式停 `DbvmTools`，其停止目前只依赖进程退出时的静态析构，见 5.5.3。
- DBVM 命中回调由 `DbvmTools` 的 resumer 线程同步触发（`include/DbvmTools.h:105`），与调试链路的 PostMessage 模型不一致，见 5.5.4。
- `Debugger` 回调目前建议 `std::function` 形式；如果未来要跨 DLL 边界，应改成稳定 C 接口或事件结构，避免 `std::function` 二进制接口膨胀。
- 反汇编引擎现状见 5.5.8 第 6 条：自研 `Disasm.cpp` 的 `db ` 兜底按 1 字节计长，会污染下游 HookRestore 对齐与 Trace Over 地址计算；换用 `thirdparty/udis86` 不自动解决该问题（`decode.c:1230-1262` 出错仍返回 `inp_ctr`），必须显式校验 `UD_Iinvalid`。

## 7. 成功标准

当满足以下条件时，可以认为重构达成目标：

- `main_gui.cpp` 不再是项目依赖中心，视图和服务各自可独立阅读。
- 同一套构建命令只产出 GUI（`bin/CEScan.exe`），产物名稳定；CLI 已按用户要求移除，不再作为目标。
- `CachedModules` 和调试线程不再靠注释约定规避竞态。
- 后台通知走统一 dispatcher，消息载荷不再使用裸指针手工 delete。
- `DbvmTools::Instance()` 在 GUI 代码中不再出现。
- `Disasm` 引擎选型完成（继续自研 / udis86 / Capstone / Zydis 四选一有明确结论），且未覆盖指令有回归测试。
- 核心逻辑有测试覆盖，附加/扫描/调试/Watch/DBVM 主路径有可重复验收。
